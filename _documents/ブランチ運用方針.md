# ブランチ運用方針

どのブランチから分岐し、どこへ PR を向け、どこでリリースするか。
各アプリ（Questionnaire など）の運用に揃えつつ、**Core の事情で変えた点は理由を明記する。**

## ブランチの種類

| ブランチ | 役割 | 直接 push | 作業の base |
|---|---|---|---|
| `develop` | 開発を集約する | 不可 | **ここ** |
| `master` | リリース確定状態を保持する | 不可（PR 必須） | 原則不可 |
| 作業ブランチ | 機能追加・修正の単位。`feature/**` `fix/**` | 可 | — |

**既定ブランチは `develop`。** `develop` と `master` を合わせて「根幹ブランチ」と呼ぶ。

| 段階 | 操作 | 実行者 |
|---|---|---|
| 開発開始 | `develop` から作業ブランチを切る | 各開発者 |
| レビュー | 作業ブランチ → `develop` へ PR | 各開発者 |
| 取り込み | 必須チェック通過後に `develop` へマージ | 各開発者 |
| リリース準備 | `develop` → `master` へ PR | リリース担当 |
| リリース | `master` へタグを付けて公開 | リリース担当（[`リリース手順書.md`](リリース手順書.md)） |

## 守ること

- **作業ブランチは `develop` から分岐させ、PR の base も `develop` にすること**

    ```bash
    git switch develop && git pull
    git switch -c feature/xxx
    gh pr create --base develop --draft --title "WIP: ..."
    ```

- **`master` を base にした PR を出さないこと**
    - リリース確定済みの状態が、レビュー前の変更で動くため
    - リリース時のみ `develop` → `master` の PR を出す
- **ドキュメントだけの変更でも PR を通すこと。** 直接 push で済ませない
- **PR 本文に `Closes #N` を書くこと**
- **ブランチ保護のバイパスを通常運用で使わないこと。** 管理者はバイパスできてしまう
- **Core の変更は全アプリへ効く。** 公開 API を変える PR は、各アプリの追随を Issue に残す
  （[`コア化の方針.md`](コア化の方針.md)）

## PR を積み上げるとき（stacked PR）

**先行する PR の変更が無いと成り立たない PR は、base を親の作業ブランチにすること。**
develop を base にして「先に #N をマージしてください」と本文へ書くのは、
依存がどこにも宣言されていない状態になる。

- **レビュー差分がその PR の分だけになる**
- **順番が GitHub 側から見える**
- ⚠️ **親が squash マージされたら、子は作り直す。** 子のブランチには元のコミット列が残るので、
  そのまま `develop` をマージすると add/add のコンフリクトになる

    ```bash
    git log --oneline --no-merges origin/develop..HEAD   # 何を運ぶか確かめる
    git checkout -B <ブランチ名>-v2 origin/develop
    git cherry-pick <子の固有コミット>...
    git push --force-with-lease origin HEAD:<元のブランチ名>
    gh pr edit <子のPR番号> --base develop
    ```

- **自動マージを armed にするのは、親が入ってから。** 子の必須チェックが先に緑になると、
  順番を無視して入り得る

## 作業ツリー（worktree）の切り方

**別ブランチの作業は、メインツリーでブランチを切り替えるのではなく `git worktree` を
切って行うこと。** 1 つの作業ツリーでブランチを切り替えると、他の作業中の変更やビルド成果物
（`bin/` `obj/`）を壊す。分岐元から直接作れば、切り忘れによる誤ったブランチへのコミットも防げる。

| 項目 | 決まり |
|---|---|
| 置き場所 | 本体リポジトリと並列の `VehicleVision.PleasanterTools.Core.worktrees/` 配下 |
| ディレクトリ名 | `{PR番号 または Issue番号}-{概要}`（英小文字のケバブケース） |
| 番号が無いとき | `unassigned-{概要}`。**採番できたらリネームすること** |

```bash
git worktree add -b feature/12-mail-options \
    ../VehicleVision.PleasanterTools.Core.worktrees/12-mail-options origin/develop
```

- 用が済んだツリーは `git worktree remove <パス>` で片付けること
    - **未 push の変更があるツリーは消さないこと。** 退避するか残すかは利用者に確認する
    - **マージ済みかどうかは PR の状態と内容で判断すること。** squash マージのため
      `git cherry` や祖先判定は当てにならない

## 一時成果物の置き場所

- 調査メモ・生成したコマンドリスト・検証用スクリプトなど**その場限りの成果物は
  `temp/{yyyyMMdd}_{内容}/` に出すこと**。`temp/` は `.gitignore` 済み

## CI の実行条件

| ワークフロー | ジョブ名（＝チェック名） | 実行契機 | 必須 |
|---|---|---|---|
| `.github/workflows/ci.yml` | `ビルドと単体テスト` | 根幹ブランチへの push、根幹ブランチを対象とする PR | ○ |
| 同上 | `SDK 指定の一致検査` | 同上 | ○ |
| 同上 | `規約の同期検査`（`scripts/sync-agents.sh --check`） | 同上 | ○ |
| `.github/workflows/pr-title-wip-check.yml` | `WIP が外れているか` | 根幹ブランチを対象とする PR（タイトルの編集も拾う） | ○ |
| `.github/workflows/pr-issue-link-check.yml` | `Issue と紐付いているか` | 根幹ブランチを対象とする PR。止めずにコメントで知らせる | — |
| `.github/workflows/cla-check.yml` | `CLA へ署名しているか` | 根幹ブランチを対象とする PR（`pull_request_target`） | — |
| `.github/workflows/dependency-review.yml` | `入ってくる依存を見る` | 根幹ブランチを対象とする PR | — |
| `.github/workflows/dependency-audit.yml` | `NuGet 依存の脆弱性検査` | 全ブランチへの push、週次、手動 | — |
| 同上 | `NOTICE と依存の整合検査`（`scripts/notice-check.sh`） | 同上 | ○ |
| `.github/workflows/codeql.yml` | `CodeQL 解析（C#）` | 全ブランチへの push、週次、手動 | — |
| `.github/workflows/release.yml` | `GitHub Packages へ公開` | `v*` タグの push | — |

- **ジョブ名を変えないこと。** 必須ステータスチェックはチェック名で照合するため、
  改名すると「待ち続けるが永遠に来ない」状態になりマージできなくなる
    - 「必須」が `—` のものも、登録する日が来たときに困るので変えないこと
- **`SDK 指定の一致検査` の基準値は各アプリと同じ**（10.0.100 / `latestFeature`）。
  各アプリの `global.json` を変えるときは、Core も同時に変えること

### CodeQL（`codeql.yml`）

**advanced setup（ワークフローを自分で持つ形）で回す。** GitHub 管理の default setup は
実行契機もクエリスイートも制御できず、上表の方針と食い違うため使わない。

| 項目 | 内容 |
|---|---|
| 対象言語 | `csharp`（実ビルドをトレース） |
| クエリスイート | `security-extended`（`.github/codeql/codeql-config.yml`） |
| 結果の置き場所 | Security タブ > Code scanning。**ジョブのログには出ない** |

- ⚠️ **アラートの題名と解説は英語のまま。** 却下（dismiss）するときの理由は日本語で書くこと

### 依存の脆弱性検査（`dependency-audit.yml`）

- ⚠️ **`dotnet list package --vulnerable` は、脆弱性を見つけても終了コード 0 を返す。**
  そのまま CI のステップにすると永遠に緑になる。JSON を読んで落とすスクリプトを挟んでいる
- **週次でも回す。** 脆弱性はこちらのコードが変わらなくても増える
- **`NOTICE` の整合検査は必須。** 直接参照する依存が `Directory.Packages.props` にあり、
  `NOTICE` に「名称 バージョン /」の行が無ければ落とす

### 依存の更新（Dependabot）

`.github/dependabot.yml` で nuget / github-actions を週次で見る。**base は `develop`。**
更新 PR にも必須チェックが適用される。

**寛容ライセンス（MIT / BSD 系 / Apache-2.0）以外へ変わった依存は入れないこと。**
採用を続けるなら [`NOTICE`](../NOTICE) を直す。

## ブランチ保護

**Repository rulesets で設定する**（classic branch protection は使わない）。

| ruleset | 対象 | ルール |
|---|---|---|
| `develop-protection` | `refs/heads/develop` | 削除禁止、force push 禁止、**必須ステータスチェック** |
| `master-protection` | `refs/heads/master` | 上記に加えて **PR 必須**（承認 0 件） |
| `release-tag-protection` | `refs/tags/v*` | 削除禁止、force push 禁止 |

- **`master` の PR 必須は承認数 0。** レビューを強制するためではなく、
  リリース確定ブランチへ直接 push が入らないようにするための設定
- **リポジトリ管理者（Repository role の Admin）はバイパスできる。** 緊急時の復旧経路を塞がないため。
  **通常運用でバイパスを使わないこと**
- `delete_branch_on_merge` を有効にする
- **ruleset を触るときは、まず現状を GET して差分だけ足すこと。**
  `PUT /repos/{owner}/{repo}/rulesets/{id}` は**送らなかったルールを消す**

### 必須ステータスチェック

| チェック名 | 出どころ |
|---|---|
| `ビルドと単体テスト` | `.github/workflows/ci.yml` |
| `SDK 指定の一致検査` | 同上 |
| `規約の同期検査` | 同上 |
| `WIP が外れているか` | `.github/workflows/pr-title-wip-check.yml` |
| `NOTICE と依存の整合検査` | `.github/workflows/dependency-audit.yml` |

**CodeQL と依存の脆弱性検査（NuGet・`dependency-review.yml`）は、あえて必須にしていない。**
どちらも「こちらのコードが変わらなくても赤くなる」検査で、新たに公開された脆弱性で
既存コードが引っかかった瞬間、**その修正 PR 自体がマージできなくなる。**
門番ではなく、気付くための仕掛けとして扱う。

- **登録したジョブ名は以後変更しない**
- `strict_required_status_checks_policy` は無効

## ラベルと Milestone

**ラベル名は `{区分番号}-{区分名}:{値}` の形式。**
