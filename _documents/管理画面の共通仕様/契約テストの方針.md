# 管理画面の契約テストの方針

[管理画面の共通仕様書](../管理画面の共通仕様書.md)の 10 章。**設計メモであり、実装はまだ無い。**
仕様書の不変条件を、**アプリに依存しない形**で、HTTP の層から確かめるための足場を決める。

## 10.1 ねらい

- 同じ不変条件を、アプリごとに書き写した試験で守ると、**試験もコピーと同じくばらつく**。
  Q#695 は「`/enroll/begin` が登録済みの人を受け付ける」欠陥で、AtomFeed・CalendarFeed には流れ自体が無かった
  （[各アプリの差異の一覧](各アプリの差異の一覧.md)）。**流れがあるアプリ・無いアプリを同じ物差しで測れる**ようにする
- 試験は**実装ではなく契約（経路・状態・本文の形・cookie）**を見る。Core.Web へ寄せる途中でも、寄せた後でも同じ試験が通ること

## 10.2 置き場所

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. Core のテスト用ライブラリ（推奨） | `VehicleVision.PleasanterTools.Core.Web.Testing`（仮）を NuGet で配り、各アプリの試験プロジェクトが参照して、自分の `WebApplicationFactory<Program>` を渡す | 不変条件を 1 か所で直せる。Core の版を上げれば全アプリに効く | アプリごとの差（経路の有無・初期データの作り方）を吸収する口が要る |
| B. 各アプリに書き写す | 各アプリの `Integration.Tests` に同じ試験を置く | すぐ始められる | **コピーが育つ**（コア化の方針の背景そのもの） |
| C. 外から叩く黒箱の試験（別リポジトリ） | 起動したアプリへ HTTP で当てる | 言語・構成を問わない（IdP も同じ物差し） | 初期データ（管理者・TOTP）を外から作れない。CI が重い |

**A を基本にし、アプリの差は「能力の宣言」で吸収する**（下記）。C は IdP のように設計が違うアプリで、
入口の存在だけを確かめる用途に限る。どれにするかは未決事項 U9。

### 10.2.1 アプリから受け取るもの（案）

```csharp
// 名前・形は案。Core に入れるときに決める
public interface IAdminContractHost
{
    HttpClient CreateClient();                         // cookie を保つクライアント
    AdminContractCapabilities Capabilities { get; }    // 2 要素・SAML・招待などの有無
    Task<SeededAdmin> SeedAdminAsync(string role, bool withTotp, CancellationToken ct);
    string NextTotpCode(SeededAdmin admin);            // 時計を固定して数字を作る
}
```

- `SeedAdminAsync` は Core の `IAdminUserStore`（`CreateFirstAsync`・`CreateAsync`・`EnableTotpAsync`）で作れる。
  Core のストアを使うアプリは共通の実装を使い回せる
- 時刻は `TimeProvider` を差し替える（Core のストアは `TimeProvider` を受ける。`Core.Data/Stores/AdminUserStore.cs:184-188`）
- 能力の宣言で「流れが無い」と言ったアプリでは、その試験は**入口が 404 であること**を確かめる（無いことも契約）

## 10.3 HTTP の層で確かめること

- 状態コード（401・403・404・409・423）と、エラー本文の形（`{message}` か `{code}`）。**文言は見ない**（言語で変わる）
- cookie の名前・属性（`HttpOnly`・`SameSite`）・中身が ID だけであること（cookie の長さや形）
- 応答の `Cache-Control`
- 監査ログに行が増えたか（`IAuditLogStore.ListAsync` で `Action`・`Succeeded`・`StatusCode` を見る。本文の秘密が入っていないこと）

## 10.4 最初に入れる不変条件の候補

| 番号 | 不変条件 | 確かめ方（HTTP） | 仕様 |
|---|---|---|---|
| C1 | **TOTP を登録済みの人は `/enroll/begin`・`/enroll/complete` を使えない**（Q#695） | 登録済みの管理者でパスワードだけ通し（`next=totp`）、Pending のまま `/enroll/begin` → 403、`/enroll/complete` → 403。`/login/totp` は従来どおり通る | T2 |
| C2 | 登録し直しはパスワードの再確認を要する | `/me/totp/begin` に誤ったパスワード → 401、5 回で 423。正しいパスワード → 200 と Reenroll の cookie | T3 |
| C3 | Reenroll と Pending は取り違えられない | Reenroll の cookie だけで `/enroll/begin`・`/login/totp` → 401。Pending の cookie だけで `/me/totp/complete` → 401 | T4・T5 |
| C4 | Pending では何も操作できない | Pending の cookie で `/users`・`/me/password`・`/audit-logs` → 401 | 4.2 |
| C5 | ログインの失敗は理由を区別しない | 居ない ID・違うパスワード・無効の人が、同じ状態と同じ本文の形（401） | 3.2 |
| C6 | 最後の有効な Administrator は無効化・降格できない | Administrator 1 人で、別の人から（または自分以外の経路で）`/disable`・`/role` → 409。招待しただけの Administrator は頭数に入らない | 6.3 |
| C7 | 役割の変更・無効化は、相手のセッションへ即座に効く | 相手のログイン済みの cookie で、役割の変更後に権限の要る口 → 401（失効）。無効化後 → 401 | 4.3 |
| C8 | cookie には ID だけが載り、役割は要求ごとに DB から読む | DB で役割を変えると、同じ cookie の次の要求から権限が変わる（または失効する） | 4.2 |
| C9 | 招待は 1 回限り・期限付き・理由を区別しない | 同じトークンを 2 回 → 2 回目 401。期限切れ・でたらめ → 同じ 401 | 3.8 |
| C10 | 権限の無い役割は、権限の要る口で 403 | 監査担当で `/users` の更新系 → 403。**`/users/{id}/totp/reset` は `users.resetTwoFactor` を要する**（現状の Q はサーバで確かめていない。未決事項 U1） | 6.2 |
| C11 | 更新系は失敗も含めて監査ログに残り、秘密が入らない | `/login` の失敗後、`Action=POST /api/admin/login`・`Succeeded=false`・`DetailJson` にパスワードが無い | 7.1 |
| C12 | `Disabled` では新しい登録の口が閉じ、登録済みの人の 2 要素は外れない | 方針 `Disabled` で `/enroll/begin` → 400、登録済みの人の `/login` → `next=totp` | 3.4 |

C1〜C5 を最初の 1 本にする（Q#695 の再発防止に直結し、AtomFeed・CalendarFeed で流れが無いことも同じ試験で表せる）。

## 10.5 段階

1. Q の `Integration.Tests` に、上の候補を **Core に移せる形**（`IAdminContractHost` 越し）で書く。Q で通ることを確かめる
2. Core に試験用のパッケージを作り、1 を移す。Q は参照へ切り替える
3. AtomFeed・CalendarFeed が参照する。**流れが無いものは 404 の確認になる**。差を Issue にする
4. IdP は能力の宣言で大半を「無い」とし、入口の有無と cookie の属性だけを確かめる（設計が違うため）
