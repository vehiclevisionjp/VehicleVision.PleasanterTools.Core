# 管理画面の契約テストの方針

[管理画面の共通仕様書](../管理画面の共通仕様書.md)の 10 章。
**C1〜C5 の共有テストを実装済み。C2 の仕様判断は完了したが、更新後の Q での実行確認は環境により停止中。未公開**（Issue #80）。
仕様書の不変条件を、**アプリに依存しない形**で、HTTP の層から確かめるための足場を決める。

## 10.1 ねらい

- 同じ不変条件を、アプリごとに書き写した試験で守ると、**試験もコピーと同じくばらつく**。
  Q#695 は「`/enroll/begin` が登録済みの人を受け付ける」欠陥で、AtomFeed・CalendarFeed には流れ自体が無かった
  （[各アプリの差異の一覧](各アプリの差異の一覧.md)）。**流れがあるアプリ・無いアプリを同じ物差しで測れる**ようにする
- 試験は**実装ではなく契約（経路・状態・本文の形・cookie）**を見る。Core.Web へ寄せる途中でも、寄せた後でも同じ試験が通ること

## 10.2 置き場所

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. Core のテスト用ライブラリ（採用） | `VehicleVision.PleasanterTools.Core.Web.Testing` を NuGet で配り、各アプリの試験プロジェクトがホストを実装して参照する | 不変条件を 1 か所で直せる。Core の版を上げれば全アプリに効く | アプリごとの差（経路の有無・初期データの作り方）を吸収する口が要る |
| B. 各アプリに書き写す | 各アプリの `Integration.Tests` に同じ試験を置く | すぐ始められる | **コピーが育つ**（コア化の方針の背景そのもの） |
| C. 外から叩く黒箱の試験（別リポジトリ） | 起動したアプリへ HTTP で当てる | 言語・構成を問わない（IdP も同じ物差し） | 初期データ（管理者・TOTP）を外から作れない。CI が重い |

**A を採用し、`VehicleVision.PleasanterTools.Core.Web.Testing` として配布する**（preview.11 予定。未公開）。
アプリの差は「能力の宣言」で吸収する。C は IdP のように設計が違うアプリで、
入口の存在だけを確かめる用途に限る。U9 の置き場所はこれで決定した。

### 10.2.1 アプリが実装するもの

```csharp
public sealed class AdminContractTests : AdminAuthenticationContractTests
{
    protected override async Task<IAdminContractHost> CreateHostAsync() =>
        await AppAdminContractHost.StartAsync();
}
```

`AppAdminContractHost` はアプリ側の実装例の名前。ホストは **1 試験ごとに作成・破棄**される。
基底クラスが持つ `Fact` / `Theory`（16 件）が、継承先の xUnit 試験として発見される。

| 公開 API | アプリが渡すもの |
|---|---|
| `IAdminContractHost` | `IAsyncDisposable`。設定・能力・HTTP クライアントと、下記の準備用ヘルパ |
| `CreateClient()` | 空の独立した cookie 容器を持つ `HttpClient`。転送を追わず、同じホストへ接続する |
| `SeedAdminAsync(withTotp, disabled)` | 管理操作の権限を持つ、一意な ID の利用者を作る。必要なら TOTP を登録・利用者を無効化する |
| `SeededAdmin` | ログイン ID とパスワード。共有テストへ鍵や DB の型は渡さない |
| `LoginAsync(client, admin)` | パスワードだけを **HTTP で**照合し、加工していない応答を返す |
| `NextTotpCode(admin)` | サーバが受け付ける未使用の時間枠の数字 |
| `AdminContractCapabilities` | 存在する `AdminContractOperation` の集合 |
| `AdminContractSettings` | 全操作の経路と方法、要求本文への変換、次の段階の項目名と値、ログイン失敗の JSON の形 |
| `AdminContractEndpoint` / `AdminContractInput` | 方法・経路と、ID・パスワード・コードなどをアプリの JSON 本文へ変換する関数 |
| `AdminContractCookies` | Session・Pending・Reenroll の異なる cookie 名 |

- `SeedAdminAsync` は Core.Data のストアでも、アプリ独自のストアでもよい。
  共有ライブラリは DB・ASP.NET Core・アプリ本体を参照しない。依存は既存と同じ xUnit 2.9.3 だけ
- 経路は接頭辞も含めてアプリが指定する。共有側は `/api/admin` と `/admin/api` を知らない。
  本文も `{password}` などを決め打ちせず変換する。状態コード・失敗回数は設定で緩められない
- 能力が「無い」場合も探査先を指定する。試験を飛ばさず **404 を要求**する。設定漏れは初期化時に失敗する
- C1〜C4 の存在する入口を試すには、パスワードと TOTP のログインが要る。
  登録し直しの完了には開始の入口も必要。矛盾した能力宣言は拒む。
  **別方式で認証する IdP への適用は未実装**。全入口が無い場合の 404 確認とは区別する
- C3 は独立したクライアントへ Reenroll の cookie だけを移し、Session が紛れ込まないようにする。
  Pending の名前へ付け替えた場合も拒否を要求する
- C5 は同じ `Accept-Language: en` で、状態と JSON の形に加えて **本文の値も一致**させる。
  翻訳の具体的な文言は共有側に置かない
- C2 は 5 回の失敗すべてに 401、直後の正しいパスワードにも締め出し中の 423 を要求する。
  上限到達の要求を 423 にする選択肢は追加しない（U15）。
  AF・CF は登録し直しの再確認が無く、IdP はこの認証方式を使わないため、設定で差を隠さず A.2 に残す
- Q の `TotpService` は時計を注入できない。Q のホストは未使用の枠で直接登録し、実時刻で数字を作る。
  時計の固定・時間切れの試験を済ませたとは扱わない

根拠（2026-10-22）:
`src/VehicleVision.PleasanterTools.Core.Web.Testing/IAdminContractHost.cs:4`、
`AdminContractSettings.cs:7,21,28,39,57,60`、
`AdminAuthenticationContractTests.cs:8,36,54,70,83,116,143,162,178`（同ディレクトリ）。
自己検証は `tests/VehicleVision.PleasanterTools.Core.Web.Tests/AdminContractTestsTests.cs:10`。
異なる経路・PUT・本文・cookie 名を与え、契約違反の応答で失敗することも検査する。

### 10.2.2 参照と公開前の確認

公開後は **アプリの試験プロジェクトだけ**から `.Web.Testing` を `PackageReference` で参照する。
アプリ本体へ追加しない。試験プロジェクトには xUnit と実行用の Test SDK / runner が別途必要。
`WebApplicationFactory` 相当の用意と破棄、試験用 DB の隔離もアプリの責任である。

公開前は次のどちらかで確かめる。**一時参照・一時フィードの設定はコミットしない。**

1. Core を `dotnet pack -c Release -p:Version=0.1.0-preview.11 -o temp/20261022_contract-tests/packages` で梱包し、
   そのフォルダを一時的な `nuget.config` のソースにして参照する
2. 試験プロジェクトに、一時的な `ProjectReference` を追加する

Q 側の導入は
[vehiclevisionjp/VehicleVision.PleasanterTools.Questionnaire#708](https://github.com/vehiclevisionjp/VehicleVision.PleasanterTools.Questionnaire/issues/708)
で追跡する。Draft では公開前の `PackageReference` を置かず、
`EnableAdminContractTests=true` と一時参照を与えた場合だけ新しい試験をコンパイルする。
**既定の CI がこの契約を検証したとは扱わない。**
公開後に正式な参照と NOTICE を追加し、この一時的なコンパイル除外を外して、全件を再実行する。

## 10.3 HTTP の層で確かめること

この節は最終的な対象。**今回実装した範囲は C1〜C5 の状態コード・認証段階・cookie の発行と分離・
ログイン失敗の JSON であり、cookie 属性・キャッシュ・監査ログの検証はまだ無い。**

- 状態コード（401・403・404・409・423）と、エラー本文の形（`{message}` か `{code}`）。**文言は見ない**（言語で変わる）
- cookie の名前・属性（`HttpOnly`・`SameSite`）・中身が ID だけであること（cookie の長さや形）
- 応答の `Cache-Control`
- 監査ログに行が増えたか（`IAuditLogStore.ListAsync` で `Action`・`Succeeded`・`StatusCode` を見る。本文の秘密が入っていないこと）

## 10.4 最初に入れる不変条件の候補

| 番号 | 不変条件 | 確かめ方（HTTP） | 仕様 |
|---|---|---|---|
| C1 | **TOTP を登録済みの人は `/enroll/begin`・`/enroll/complete` を使えない**（Q#695） | 登録済みの管理者でパスワードだけ通し（`next=totp`）、Pending のまま `/enroll/begin` → 403、`/enroll/complete` → 403。`/login/totp` は従来どおり通る | T2 |
| C2 | 登録し直しはパスワードの再確認を要する | `/me/totp/begin` に誤ったパスワード → **5 回目も通常と同じ 401**、**その次の要求から 423**（正しいパスワードでも拒む）。締め出し前の正しいパスワード → 200 と Reenroll の cookie。期間は設定による（6.4） | T3 |
| C3 | Reenroll と Pending は取り違えられない | Reenroll の cookie だけで `/enroll/begin`・`/login/totp` → 401。Pending の cookie だけで `/me/totp/complete` → 401 | T4・T5 |
| C4 | Pending では何も操作できない | Pending の cookie で `/users`・`/me/password`・`/audit-logs` → 401 | 4.2 |
| C5 | ログインの失敗は理由を区別しない | 居ない ID・違うパスワード・無効の人が、同じ状態と同じ本文の形（401） | 3.2 |
| C6 | 最後の有効な Administrator は無効化・降格できない | Administrator 1 人で、別の人から（または自分以外の経路で）`/disable`・`/role` → 409。招待しただけの Administrator は頭数に入らない | 6.3 |
| C7 | 役割の変更・無効化は、相手のセッションへ即座に効く | 相手のログイン済みの cookie で、役割の変更後に権限の要る口 → 401（失効）。無効化後 → 401 | 4.3 |
| C8 | cookie には ID だけが載り、役割は要求ごとに DB から読む | DB で役割を変えると、同じ cookie の次の要求から権限が変わる（または失効する） | 4.2 |
| C9 | 招待は 1 回限り・期限付き・理由を区別しない | 同じトークンを 2 回 → 2 回目 401。期限切れ・でたらめ → 同じ 401 | 3.8 |
| C10 | 権限の無い役割は、権限の要る口で 403 | 監査担当で `/users` の更新系 → 403。**`/users/{id}/totp/reset` は `users.resetTwoFactor` を要する**（現状の Q はサーバで確かめていない。未決事項 U1） | 6.2 |
| C11 | 更新系は失敗も含めて監査ログに残り、秘密が入らない | `/login` の失敗後、`Action=POST /api/admin/login`・`Succeeded=false`・`DetailJson` にパスワードが無い | 7.1 |
| C12 | `Disabled` では新しい登録の口が閉じ、登録済みの人の 2 要素は外れない | 方針 `Disabled` で `/enroll/begin` → 400、登録済みの人の `/login` → `next=totp` | 3.4 |

C1〜C5 を最初の 1 本にする（Q#695 の再発防止に直結し、AtomFeed・CalendarFeed で流れが無いことも同じ試験で表せる）。

## 10.5 段階

1. Core に C1〜C5 の共有パッケージを作り、Q の `Integration.Tests` にホストと継承クラスを置く（実装済み）
2. Q で全契約が通ることを確かめ、公開後に正式な NuGet 参照へ切り替える（C2 の判断済み。更新後の実行確認と公開待ち）
3. AtomFeed・CalendarFeed が参照する。**流れが無いものは 404 の確認になる**。差を Issue にする
4. IdP は能力の宣言で大半を「無い」とし、入口の有無と cookie の属性だけを確かめる（設計が違うため）

### 10.5.1 Q での結果と仕様の決定

変更前の検証（2026-10-22）は、Q `004766d` を基点に、実際の `Program` を `WebApplicationFactory` で起動した。
試験ごとに専用の SQLite DB へ本体のマイグレーションを当てる。送信ワーカーは外し、
認証・認可・管理 API・ストアは本体を使う。本体コードは変更していない。
一時的な `ProjectReference` と、ローカルで pack した NuGet の参照の両方で、同じ結果になった。

| 契約 | 件数 | 結果 |
|---|---|---|
| C1 | 2 | 成功。登録の開始・完了は 403、その後も元の TOTP でログイン可能 |
| C2 | 4 | 3 成功・1 失敗。未指定・誤ったパスワードは 401、正解は 200 と Reenroll cookie |
| C3 | 6 | 成功。cookie 単独・名前の付け替えで認証段階を取り違えられない |
| C4 | 3 | 成功。Pending の管理者一覧・パスワード変更・監査一覧は 401 |
| C5 | 1 | 成功。存在しない人・誤り・無効の人は同じ 401 と本文 |

変更前の C2 の不一致は、5 回の失敗がすべて 401 となり、次の正しいパスワードで 423 になることだった。
DB 上の締め出しは作動している。2026-10-22 のユーザー判断で、**仕様を Q の実装に合わせる**と決定した（U15）。
上限に達した失敗の要求自体は通常と同じ 401（理由を区別しない）、**その次の要求から 423**。
期間は設定による（Q の既定は 15 分、外部設定の可否は 6.4）。Q 本体は変更しない。
`Q.Web/Services/AdminAuthenticator.cs:154-165,452-465`（1.2 の基点）を読み直して確認した。
共有 C2 の期待を変更し、自己検証には「5 回目以前の 423」と「6 回目も 401」を拒む例を追加した。

**更新後の再検証（2026-10-22）は未完了**。
Q `fef6861` の `Integration.Tests` に、一時 MSBuild targets でローカル NuGet
`0.1.0-preview.11-contract80-20261022` を参照させた（参照設定はコミットしない）。
コンパイルは成功したが、Windows Code Integrity が `Core.Web.Testing.dll` の読み込みを
`0x800711C7` で拒み、契約 16 件は探索できず実行されなかった。
短いパスへ Q のソースを複製し再ビルドしても同じだったため、**16 件成功とは扱わない**。
Core も Release ビルドは警告 0・エラー 0、Mail 45 件・Data 86 件は成功したが、
Web の契約自己検証は同じ読み込み拒否で停止した。Core の短いパスでの再ビルドでも解消していない。
一方、同じ変更の Core `eb7a935` は
[Linux CI](https://github.com/vehiclevisionjp/VehicleVision.PleasanterTools.Core/actions/runs/39705450252)
で Release ビルドが警告 0・エラー 0、全 266 件（Web 135・Mail 45・Data 86）が成功、スキップ 0 と確認できた。
第 2 段階は、実行可能な環境で Q の 16 件を再検証するまで未完了。

SQL Server・Pleasanter 実機・Redis・他アプリの HTTP 動作は未検証（ロックアウトのソース確認結果は A.2）。
SQL Server 前提の既存 E2E を実行した結果ではない。
